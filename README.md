# @soft-advisor/env-sources

Resolve an app's environment variables at deploy time from explicit sources, such as AWS Systems Manager Parameter Store, and validate them with the app's own schema.

- **Explicit.** Every variable is mapped to its source by name in your deploy code, so reading it tells you exactly what the app consumes and where each value comes from.
- **Validated before anything deploys.** Values are checked against the schema the app itself uses (Zod, Valibot, ArkType or any other [Standard Schema](https://standardschema.dev) validator), and every problem is reported at once, without the values.
- **Not tied to a deployment tool.** It returns plain objects of strings. Pass them to SST, CDK, Pulumi, an ECS task definition or a script.
- **No dependencies.** Reading Parameter Store goes through a function you provide; the optional `/ssm` entry point makes one from an AWS SDK v3 client.

## Install

```sh
pnpm add -D @soft-advisor/env-sources
pnpm add -D @aws-sdk/client-ssm # for the /ssm helper
```

## Usage

Declare the variables your app needs as schemas, shared by the app and its deploy code:

```ts
// env/server.ts
export const serverEnv = z.object({
  SESSION_SECRET: z.string().min(32),
  ALPHA_EMAILS: z.string(),
  PARTNER_API: z
    .string()
    .transform((json) => JSON.parse(json))
    .pipe(z.object({ url: z.url(), apiKey: z.string() })),
});
```

Then, in the deploy code, map each variable to its source and resolve it:

```ts
import { SSMClient } from '@aws-sdk/client-ssm';
import { createResolver, fromSsmParameter } from '@soft-advisor/env-sources';
import { ssmParameterReader } from '@soft-advisor/env-sources/ssm';

const resolver = createResolver({
  readSsmParameter: ssmParameterReader(new SSMClient({ region: 'eu-west-2' })),
});

const serverVars = await resolver.resolve(serverEnv, {
  SESSION_SECRET: fromSsmParameter('/my-app/session-secret'),
  ALPHA_EMAILS: fromSsmParameter('/my-app/alpha', 'emails'),
  PARTNER_API: fromSsmParameter('/shared/partner', 'api'),
});
// { SESSION_SECRET: '...', ALPHA_EMAILS: '...', PARTNER_API: '{"url":...}' }
```

### Sources

| Source                          | Value                                                                                                                                                                |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'production'`, `process.env.X` | The value itself.                                                                                                                                                    |
| `undefined`                     | The variable is left out. The schema decides whether that's allowed.                                                                                                 |
| `fromSsmParameter(name)`        | The parameter's whole value, decrypted.                                                                                                                              |
| `fromSsmParameter(name, field)` | One top-level field of a parameter holding a JSON object. A field holding anything but a string (an object, a number) is passed on as JSON, for the schema to parse. |

- Each parameter is read once per resolver, however many variables and `resolve` calls use it.
- A mapped parameter or field must exist. To set a variable only in some environments, map it conditionally, e.g. `...(isProduction && { SENTRY_DSN: fromSsmParameter('/shared/sentry', 'dsn') })`, and make it optional in the schema.

### Types

The mapping is typed from the schema: every required variable must be mapped, optional ones may be left out, and unknown names are rejected.

### Validation and errors

`resolve` returns the values as strings, exactly as they should be set in an environment. The schema only checks them; its output (e.g. `PARTNER_API` parsed into an object) is for the app, which validates its environment again with the same schema at runtime.

If anything fails, `resolve` throws an `EnvSourcesError` whose `problems` list every missing parameter or field, invalid JSON and schema issue. Messages name variables and parameters, never values.

### Values created during the deploy

Some values only exist once the deploy runs, such as a password generated by Pulumi or the URL of an API created in the same app. These can't be resolved beforehand: leave them out of the schema you pass to `resolve` (e.g. with Zod's `.omit()`) and set them yourself. The app's own validation still checks the full schema.

### With SST and Next.js

```ts
async run() {
  const { createResolver, fromSsmParameter } = await import('@soft-advisor/env-sources');
  // ...create the resolver as above

  // NEXT_PUBLIC_* and build-only values are needed by `next build`, not by the Lambda.
  // SST's build inherits its own process environment, so set them there.
  const publicVars = await resolver.resolve(publicEnv, { NEXT_PUBLIC_APP_ENV: $app.stage });
  const buildVars = await resolver.resolve(buildEnv, {
    SENTRY_AUTH_TOKEN: process.env.SENTRY_AUTH_TOKEN,
  });
  Object.assign(process.env, publicVars, buildVars);

  // Runtime values go to the server function (and the build)
  const serverVars = await resolver.resolve(serverEnv, {
    SESSION_SECRET: fromSsmParameter('/my-app/session-secret'),
  });
  new sst.aws.Nextjs('Web', { environment: serverVars });
}
```

SST up to at least 4.17.2 stores the build's whole environment in its state unencrypted ([anomalyco/sst#6996](https://github.com/anomalyco/sst/issues/6996)). Until it's fixed, mark it secret with a Pulumi stack transformation, as described in that issue.

## Releasing

The package publishes itself when its `package.json` version isn't on npm yet: bump the version in a PR, and merging it to `main` publishes ([`publish.yml`](.github/workflows/publish.yml)). It's published from GitHub Actions with npm provenance, so each version links to the commit and workflow that built it.

**Publishing credentials.** npm trusted publishing (GitHub OIDC, no token) can only be set up for a package that already exists. So:

1. The first version is published with the organization's npm token (the `XYZ` organization secret).
2. Then, on npmjs.com, the package's Settings → Trusted publisher is set to GitHub Actions, organization `soft-advisor`, repository `env-sources`, workflow `publish.yml`.
3. The `NODE_AUTH_TOKEN` env is removed from `publish.yml`. Later versions publish through OIDC.
